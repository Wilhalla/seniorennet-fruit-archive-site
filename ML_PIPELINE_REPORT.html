Seniorennet Fruit Archive: Multimodal Topic Atlas Pipeline

This report documents the current machine-learning pipeline used to build the archive atlas from blog text and images. The goal is to produce useful topic clusters for a historic fruit archive where many posts are image-heavy and the text is often short captions.

Executive summary

The pipeline now treats text and images as peer signals. Every post can receive a text embedding, a raw image embedding, and an embedded visual-concept representation derived from image/text CLIP similarity. Posts are first assigned to broad archive categories, then clustered within those categories using cosine-distance agglomerative clustering. This avoids one global clustering problem where travel, fruit, family, animals, and garden posts interfere with each other.

Inputs and normalization

The pipeline starts from archive posts and normalizes them into a stable internal structure:

  • Post identity: id, slug, URL.
  • Text: title, excerpt, cleaned body text.
  • Time: normalized date, year, month, season.
  • Media: local paths to images in public/archive-images/....

HTML tags are removed, whitespace is normalized, and common archive/spam/noise words are excluded from keyword-based labels. This matters because the original archive contains continuation posts, imported HTML, old reactions, and photo-album style entries.

Text embeddings

ChoiceReason
BAAI/bge-m3Strong general-purpose multilingual embedding model; handles Dutch archive text better than older English-only models.
sentence-transformersRuns locally on CPU; no API dependency; deterministic enough for static preprocessing.
Input = title + excerpt + body sampleKeeps the author’s own text dominant while avoiding very long noisy tails such as reactions/spam.

Text embeddings turn each post’s language into a vector where semantically similar posts should be closer together.

Image embeddings

ChoiceReason
sentence-transformers/clip-ViT-B-32CPU-friendly CLIP model already compatible with the local stack. It is not the strongest possible visual model, but it can run on this laptop.
Embed every imageMany archive posts are primarily photographic; ignoring images would make those posts nearly invisible to topic modeling.
Average image vectors per postCreates one compact post-level visual vector from potentially many images. This is simple and scalable, though imperfect for mixed albums.

The image vector represents visual similarity directly: apples should be closer to apples, churches closer to churches, groups of people closer to other group photos, etc.

Visual concept extraction

Raw image embeddings are useful but hard to label. The pipeline therefore compares each image vector against a curated bank of CLIP text prompts, such as: 

appels
peren
pruimen
bessen
snoeien & enten
reizen & erfgoed
kerken & kastelen
musea & steden
mensen & familie
dieren & insecten
documenten

This produces lightweight visual concepts for every image. These concepts are then summarized per post and converted into text such as: 

Beeldinhoud: reizen & erfgoed, kerken & kastelen, musea & steden.

That visual-concept sentence is embedded with the same text embedding model. This gives the clusterer a semantic bridge between image content and Dutch archive concepts without requiring a heavy generative vision-language model.

Multimodal fusion

Each post can have three vector representations:

  1. Text vector from title/excerpt/body.
  2. Raw image vector from CLIP image embeddings.
  3. Visual-concept vector from CLIP-derived visual concepts embedded as text.

The current fusion method is weighted concatenation followed by L2 normalization:

final_vector = normalize(concat(
  text_vector           * text_weight,
  image_vector          * image_weight,
  visual_concept_vector * visual_semantic_weight
))

Defaults:

text_weight = 1.0
image_weight = 1.0
visual_semantic_weight = 1.0

Short, image-heavy posts receive extra image influence. This is intentional: a post with twelve images and one short caption should not be treated as weak text; the images are the post.

Broad category classification

Before clustering, posts are assigned to a broad category using a lightweight rule-assisted classifier. It uses both text terms and visual concepts.

This preprocessing step is deliberately not pure ML. Archive domains often have obvious high-level structure. Encoding that structure reduces nonsense clusters and makes the downstream ML problem easier.

Clustering algorithm

Current default: category-aware agglomerative clustering

The current default is not one global KMeans run. Instead:

  1. Split posts into broad category buckets.
  2. Inside each bucket, cluster final multimodal vectors.
  3. Use cosine distance because embeddings are directional semantic vectors.
  4. Merge tiny clusters into the nearest larger cluster.

Algorithmically, agglomerative clustering starts with each post as its own cluster and repeatedly merges the closest clusters until a distance threshold is reached. We use average linkage over cosine distance.

Why agglomerative clustering?

ReasonExplanation
No forced global geometryUnlike KMeans, it does not assume spherical clusters around centroids.
Works on cosine distancesGood fit for normalized text/image embeddings.
CPU-friendly at this archive size~3k posts is manageable locally; the expensive part is image embedding, not clustering.
Category-local thresholdsTravel posts and fruit posts can form clusters independently instead of competing in one space.

Why not global KMeans?

KMeans always forces every post into exactly one of K clusters. That produced flat and sometimes unnatural themes, such as travel posts labeled by repeated terms like “Rijden, Kerk, Antwerpen”. It also mixes broad themes with fine themes because the whole archive is compressed into one clustering problem.

Why not rely only on HDBSCAN?

HDBSCAN was tried as the preferred density-based option, but on this corpus it often produced very few large/skewed clusters and then required a fallback. That indicates the embedding space is not naturally density-separated enough at the global level. HDBSCAN remains available in legacy/global mode, but it is not currently the best default for this archive.

Topic labeling

A cluster label is built from:

  • the broad category label, e.g. Reizen & erfgoed;
  • cluster-specific frequent text terms;
  • cluster-specific visual concepts.

Example labels:

Reizen & Erfgoed, Antwerpen, Kerk, Voc, Noorwegen
Fruit & Rassen, Appels, Pruimen, Lescovacz
Tuin & Teelt, Arboretum, Tuin, Museumtuin
Mensen & Familie, Ludo, Jonathan, Tinneke

This is still not as good as true LLM labeling, but it is a major improvement over raw keyword-only labels. Future improvement: send representative titles, excerpts, and image concepts for each cluster to an LLM and ask it to produce a concise Dutch archive label.

2D atlas projection

The final multimodal vectors are projected to two dimensions with UMAP. UMAP is used only for visualization, not as the source of truth for topic labels.

ChoiceReason
UMAPPreserves local neighborhoods well, giving a map where nearby posts are usually related.

Known limitations and future improvements

  • Image averaging can blur mixed albums. A future version could use multiple image prototypes per post or max/attention pooling.
  • CLIP ViT-B/32 is CPU-friendly but old. Better models such as SigLIP or Jina CLIP v2 may improve visual semantics, if they can run acceptably on the laptop.
  • Labels are still heuristic. LLM-based cluster naming would produce more natural labels such as “Culturele daguitstappen” instead of lists of terms.
  • Category rules need tuning. The taxonomy is intentionally editable and should evolve as bad clusters are observed.
  • OCR is not included. Document/sign images could become much better with OCR text extraction.
